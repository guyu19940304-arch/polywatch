# SQLite 存储、空间诊断与离线压缩

## 保留期与磁盘空间

30 天是历史明细和曲线的滚动时间范围，**不是磁盘空间上限**。高频钱包在 30 天内可以产生大量真实交易；启动后的历史回填也会持续增加数据库。当前持仓及最后一次官方累计摘要单独保留。没有因为达到容量阈值而静默截断、抽样或删除未过期交易。

必须分别核对数据库、`-wal`、Docker 日志/镜像以及整机占用。系统磁盘已用空间不能直接归因于该应用。此项目不能仅凭一张整机监控截图确定其他服务器的 20 GB 来自哪里。

## 本次修复

- 新数据库的 `activities` 使用普通 ROWID 表。旧布局使用宽复合主键的 WITHOUT ROWID 表，导致宽主键在二级索引中重复、部分小 JSON 触发 4 KiB 溢出页。本机只读样本约 26.5 万条活动，JSON 有效内容约 186 MB，而表及其索引约 1.45 GB；这证明存在布局放大，但不是其他服务器的归因结论。
- 活动 JSON 不再重复存储独立列中的 `id` / `contentKey`，读取时完整恢复。较大的 JSON 使用带版本标记的无损压缩；接口返回格式不变，旧 JSON 仍可读。
- 相同状态、曲线点和同步时间不重复更新；没有变化的轮询不会重写整批活动。
- 到期清理使用增量回收，每次最多回收 16 MiB 或执行约 100 ms，然后尝试截断 WAL。正在持有读取快照的连接可能阻止 WAL 截断；该限制是回收预算，**不是数据库或 WAL 的硬上限**。
- 不在服务启动时重建庞大的活动表，不对用户库运行全库 `VACUUM`。旧库要立即获得新布局的空间收益，使用下面的离线复制流程；原库在线继续工作时，仍保持旧活动表布局，未来重复访问的 JSON 会逐步紧凑化，过期数据正常清理。
- schema 版本为 2。旧版程序不认识新压缩格式，不应直接降级打开新库；回滚需要还原升级前备份。

## 安全离线压缩

先正常停止服务，确保没有其他进程写入该数据库。不要手工删除 `-wal`：它可能含有尚未写回主文件的已提交数据。若工具报告 WAL 未收束，先检查服务是否确实停止，正常关闭数据库后再试。

```sh
node server/store.mjs compact /data/polywatch.sqlite /data/polywatch.compact.sqlite
```

工具行为：

1. 源数据库仅以只读方式打开，输出必须是不存在的新路径。
2. 输出磁盘至少需要“源文件大小 + 64 MiB”的可用空间；不足时在创建新数据库前拒绝执行。可以把输出放在有足够空间的另一个磁盘。这是保守预检，磁盘被其他程序占用仍可能使复制失败。
3. 逐条复制所有记录，包括尚未按日常保留策略清理的记录；不会为了缩小体积丢弃记录。新库采用紧凑布局，保留原分页签名密钥、交易 ID、重复成交次数、采集游标和所有来源口径的曲线点。
4. 核对每张表的记录数及全部记录解码后的 SHA-256 逻辑内容摘要，运行 SQLite `integrity_check`。成功时输出源/目标字节数、各表计数及摘要。发生错误时原库保留；未完成的输出不能用于替换。
5. **工具不会覆盖、删除、重命名或自动切换原数据库。** 核对成功结果后，部署者在服务仍停止时备份原库，再将新文件放到原路径；保留备份直至新版启动及数据核验完成。注意恢复原卷的文件属主/权限。

对于本仓库的 Compose，先拉取新版镜像并停止主服务，再用同一数据卷运行工具：

```sh
docker compose pull
docker compose stop dashboard
docker compose run --rm --no-deps dashboard node server/store.mjs compact /data/polywatch.sqlite /data/polywatch.compact.sqlite
```

这一步仅生成并验证副本，不会完成替换。部署者核对输出、保存原库备份并切换文件后，再运行 `docker compose up -d`。如果只想继续使用原库，也可直接启动，原库不会被工具改变。不要启动两个采集器同时操作待压缩数据库。复制与备份占用需要计入可用空间；把备份留在同一块磁盘上不会立即降低总占用。若空余空间不足，先把输出/备份放到其他磁盘，不要强行原地重建。

## 验证范围

自动回归使用 D 盘临时真实 SQLite 文件，覆盖：宽记录布局放大、离线复制保留所有交易及旧游标、低空间/已有输出/WAL 拒绝、相同轮询不额外写入、30 天到期后的实际文件缩小，以及旧/新盈亏口径隔离。30 天以内仍在保留期的真实活动不会因为这些测试或空间优化被删除。

2026-11-04 本机完整数据库验证：先通过只读 SQLite backup 取得包含残留 WAL 的一致性副本，再对副本离线压缩，原主库和 WAL 的大小及修改时间未变。289,493 条活动、721 个曲线点、1 份快照、1 份采集状态和1条同步记录全部保留；文件从 **1,592,856,576 字节降至 442,183,680 字节，减少 72.24%**。活动表溢出页为 0，`integrity_check` 为 `ok`。

另外按主键顺序遍历全部 289,493 条活动，解码并补回 `id` / `contentKey` 后做稳定键排序的全量 SHA-256 核对；活动、快照、曲线点、采集状态、同步记录、metadata 六张表的逻辑摘要均相同。唯一按预期归一化的 schema 差异是版本 `1 → 2` 与旧曲线点补充 `basis=polymarket-position-pnl`。金额、重复成交笔数和采集检查点没有改变。此结果来自该本机数据集，不是其他钱包或服务器的固定压缩率保证。
